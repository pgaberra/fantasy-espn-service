# Decision log

Non-obvious choices in fantasy-espn-service, one line each. The format and rules are in the
monorepo root's `DECISIONS.md`; choices that span repos go there.

---

[2026-09-11] fantasy-espn-service: `docker-compose.yml` runs `postgres:16-alpine` to match the staging and prod databases (both 16), not 17. Rejected: moving the servers to 17, a data migration on two databases for nothing this service uses. A local volume created under 17 will not start on 16 and has to be recreated (`docker compose down -v`).
[2026-09-11] fantasy-espn-service: only a dedicated `EspnUpstreamException`, thrown by `EspnFantasyClient`, `EspnPlayerClient` and `EspnLeagueService` when a league comes back with no settings object, answers 502, and `IllegalStateException` falls to the catch-all 500 (#21). A league with no settings counts as upstream because ESPN answered with a document we cannot read. Rejected: telling ESPN failures apart by message or cause, because the JDK type means nothing on its own (db-service maps it to 409) and a string check breaks silently.
[2026-09-11] fantasy-espn-service: `.github/dependabot.yml` is a verbatim copy of fantasy-bff's and fantasy-db-service's (gradle + github-actions, weekly, one group each), and one catch-up bump to their versions landed first (fantasy-workspace#59). Rejected: switching Dependabot on at the old versions, which would make its first PR Boot 4.0→4.1, Sentry 8.16→8.53 and four action majors in one.
[2026-09-11] fantasy-espn-service: `TOKEN_ENCRYPTION_KEY` has no default, and `TokenCipher` decodes and checks it once in its constructor (set, base64, 32 bytes), so a bad key stops startup (#20). Before shipping, staging and prod were checked to hold a 44-character key that decodes to 32 bytes, without printing it. Rejected: `@Validated` constraints on `EspnProperties`, which cannot say "decodes to 32 bytes" without a custom validator and would still leave `TokenCipher` decoding the key on every call.
[2026-09-13] fantasy-espn-service: a busy `EspnPlayerSyncService.sync()` returns empty instead of throwing, and the nightly scheduler logs that overlap as a skip at INFO, ported from fantasy-yahoo-service#49. Rejected: an `isRunning()` pre-check in the scheduler, which leaves a check-then-act gap, and keeping the throw with a quieter log, which would also quieten real failures sharing the catch.
[2026-09-15] fantasy-espn-service: the sync's headshot check runs only where `players.avatars.enabled` (`PLAYER_AVATARS_ENABLED`, the BFF's variable, default false) is on, and `ESPN_VERIFY_HEADSHOTS` is gone — whether we touch ESPN's photographs is one decision, and while the BFF strips them (fantasy-bff#236) one HEAD per player per sync to ESPN's CDN is traffic for pictures nobody sees; rejected: keeping a separate switch (two variables to keep in step for one decision), dropping the URLs while off (a BFF flipped on before this service would show no pictures at all rather than a few initials), and deleting the check (it is what keeps a sixth of the pool from loading a 404 once pictures are licensed).
[2026-09-16] fantasy-espn-service: no endpoint returns a user's stored `espn_s2`/`SWID` cookies, not even to their owner; `GET /api/v1/espn/credentials/values` is removed — the cookies are the user's ESPN session, and the read-back only prefilled masked form fields, so any XSS or stolen SlapStat session could become a stolen ESPN login; masking the values in the response (last four characters) was rejected as keeping an endpoint whose only use is showing dots.
[2026-09-16] fantasy-espn-service: the container runs as `app` with a fixed UID/GID of 10001, given numerically to `USER`, instead of root — the base image's existing `ubuntu` user (1000) was rejected as an account the image's maintainers own and may change, and handing the user a writable `/app` was rejected because the service writes only to `java.io.tmpdir` (/tmp), so the unpacked jars stay root-owned and read-only to it.
[2026-09-17] fantasy-espn-service: `GET /api/v1/espn/leagues/{id}/free-agents` reads the league-scoped player document with an `x-fantasy-filter` status filter (FREEAGENT + WAIVERS) through the same `fetch` as every other league read, and the position/club maps moved to `player/EspnPlayerFields` (fantasy-web#751) — deriving availability from `mRoster` and subtracting was rejected as a dozen calls to compute what one answers, and it cannot tell waivers from a free agent; a second copy of the position maps in the league service was rejected because two documents carry the same player shape, so a copy is a position that goes wrong in one place only.
[2026-09-22] fantasy-espn-service: `GET /leagues/{id}/teams` returns the teams in `settings.draftSettings.pickOrder` (one call, views `mTeam` + `mSettings`), because the draft setup imports teams from it and ESPN lists them by id; teams the order does not name follow in ESPN's order — the same fix as fantasy-yahoo-service's the same day, rejected: ordering in the BFF or web, which would need the order exposed as a second field every consumer must remember to apply.
